## ADR-001: MSA vs 모놀리식

### 결정
MSA 6개 비즈니스 서비스 + 3개 인프라 서비스 + 1개 챗봇 서비스

### 이유
- 포트폴리오 목적: Spring Cloud 생태계(Gateway, Eureka, Config, Kafka, Redis)를
  실무 수준으로 경험하고 증명해야 함
- 도메인 분리가 자연스러움: 견적/현장/매입/세금계산서는 각각 독립적인 비즈니스 맥락
- 학습 목적: 서비스 간 통신, 분산 트랜잭션, 이벤트 드리븐 패턴을 직접 겪어봐야 함

### 고려한 대안
- 모놀리식 → 빠르지만 포트폴리오 가치 낮음
- 모듈러 모놀리스 → 좋은 중간점이나 Spring Cloud 경험 불가
- 3~4개 서비스 → 현실적이지만 기술 경험 범위 좁음

### 트레이드오프
- 1인 개발에 MSA는 과도함. 개발 속도가 느려질 것
- 하지만 목적이 "학습 + 포트폴리오"이므로 의도적 선택
- 실사용에 문제가 되면 나중에 서비스를 
- 합칠 수 있음

## ADR-002: Kafka vs RabbitMQ vs Redis Pub/Sub

### 결정
Apache Kafka (KRaft mode)

### 이유
- 메시지 영속성: 디스크에 저장되어 소비자가 다운되어도 메시지 유실 없음
- 리플레이 가능: offset을 되돌려 과거 이벤트를 재처리할 수 있음
- 대용량 트래픽 포트폴리오: Kafka 경험이 백엔드 채용 시장에서 높은 가치
- KRaft mode: ZooKeeper 없이 운영 가능하여 로컬 환경 간소화

### 고려한 대안
- RabbitMQ: 가볍고 설정 쉬움. 하지만 메시지 리플레이 불가, 포트폴리오 가치 낮음
- Redis Pub/Sub: 가장 가볍지만 메시지 영속성 없음. 소비자 다운 시 유실

### 면접 답변
"RabbitMQ도 고려했지만, Kafka를 선택한 이유는 세 가지입니다.
첫째 메시지 영속성으로 유실 방지, 둘째 offset 기반 리플레이로 장애 복구,
셋째 Consumer Group으로 수평 확장이 가능하기 때문입니다."

## ADR-003: Redis 사용 범위

### 결정
캐시 + JWT 블랙리스트 + 분산락 (3가지 용도)

### 이유
- 캐시: 현장 목록/손익 조회가 빈번. DB 부하 줄이고 응답 속도 개선
- JWT 블랙리스트: Stateless JWT의 로그아웃 문제 해결
- 분산락: MSA 환경에서 동시 수정 방지 (Redisson)

### 패턴
- Cache Aside: 조회 시 Redis 확인 → 없으면 DB 조회 후 Redis 저장
- TTL 5분: 데이터 신선도와 캐시 효율의 균형점

### 면접 답변
"Redis를 세 가지 용도로 사용합니다.
Cache Aside 패턴으로 조회 성능 최적화, JWT 블랙리스트로 로그아웃 구현,
Redisson 분산락으로 동시 수정 방지입니다.
특히 분산락은 MSA에서 같은 견적서를 동시에 수정하는 것을 방지하기 위해 사용했습니다."

## ADR-004: Database per Service — 단일 MySQL 인스턴스

### 결정
MySQL 1개 인스턴스, 서비스별 스키마 분리

### 이유
- 로컬 개발 환경에서 MySQL 인스턴스 여러 개 띄우면 리소스 낭비
- 스키마 분리만으로도 논리적 격리 달성 가능
- 운영 환경에서 인스턴스 분리로 전환하려면 접속 정보만 바꾸면 됨

### 면접 답변
"로컬 환경 제약으로 MySQL 1개에 스키마를 분리했습니다.
각 서비스는 자기 스키마만 접근하고, 다른 서비스 데이터는 API로 조회합니다.
운영 환경에서 인스턴스를 분리하려면 Config Server의 접속 정보만 바꾸면 됩니다.
이게 Spring Cloud Config를 쓰는 이유이기도 합니다."

## ADR-005: Java 17 vs 21

### 결정
Java 17 (LTS)

### 이유
- Spring Boot 3.x의 최소 요구 버전
- 대부분의 기업 환경이 아직 17 기반
- Virtual Thread(21)는 이 프로젝트 규모에서 체감 어려움

### 트레이드오프
- 21의 Virtual Thread, Pattern Matching 등 최신 기능 못 씀
- 하지만 안정성과 호환성이 더 중요한 선택

## ADR-006: 챗봇 — RAG 방식 (벡터DB 없이)

### 결정
정형 데이터는 SQL 조회 → LLM 컨텍스트 주입. 벡터DB 미사용.

### 이유
- 데이터 대부분이 정형(MySQL): 현장명, 금액, 날짜, 상태
- 정형 데이터를 벡터로 변환하면 오히려 정확도 하락
- LLM function calling으로 의도 파악 → 적절한 API 호출 → 결과 주입이 더 정확
- 비정형 데이터(하자보증보험 PDF)가 많아지면 그때 벡터 검색 추가

### 면접 답변
"RAG라고 하면 보통 벡터DB를 떠올리지만, 이 프로젝트의 데이터는 대부분 정형 데이터입니다.
금액, 날짜, 현장명 같은 데이터를 벡터 임베딩하면 오히려 정확도가 떨어집니다.
LLM의 function calling으로 질문 의도를 파악하고, 적절한 SQL 쿼리 결과를
컨텍스트에 주입하는 방식이 이 도메인에서는 더 효과적입니다."

## ADR-007: 공내역서/견적서 — AI 자동 생성 안 함

### 결정
공내역서와 견적서는 각각 독립적으로 파일 업로드. AI가 하나를 보고 다른 걸 생성하지 않음.

### 이유
- 견적서의 단가는 현장 상황, 거래 관계, 시장 가격 등을 종합해서
  사람이 직접 판단해야 하는 영역
- 공내역서는 발주처가 보낸 원본 그대로 보관하는 문서
- 두 문서는 항목이 비슷할 수 있지만, 단가/금액은 완전히 다름
- 자동 생성하면 잘못된 견적이 나갈 위험

### 시스템에서의 역할
- 공내역서: 원본 파일 업로드 + 보관 + 뷰어
- 견적서: 파일 업로드 + 금액 데이터(total_amount) 저장 → 매출 계산 기준

## ADR-009: 프론트엔드 상태 관리

### 결정
Zustand (클라이언트 상태) + TanStack Query (서버 상태)

### 이유
- Redux Toolkit은 이 규모에 과도한 보일러플레이트
- Zustand는 가볍고 직관적. 전역 상태(로그인 유저, 사이드바 토글 등)에 적합
- TanStack Query는 서버 데이터 캐싱, 자동 리페치, 로딩/에러 상태 관리가 내장
- 두 라이브러리의 역할이 겹치지 않아 조합이 깔끔

## ADR-010: 개발 워크플로우 시스템 (BACKLOG/RETROSPECTIVE/plans + 5+1 단계 사이클)

### 결정

작업 진행과 의사결정을 **문서 기반 사이클**로 강제. 사이클: 백로그 → 계획 → 구현 → 결과 반영 → 회고 → PR 생성.

### 배경

2026-06-10까지는 진행 상황을 `.claude/PROGRESS.md` 1개에 누적. 결과:
- "다음 작업" 우선순위가 PROGRESS / 메모리 / docs/REVIEW에 분산
- 실패 케이스("PR #19 push 누락 사고")가 임시 메모로만 남아 같은 실수 재발 위험
- 작업 시작 전 계획이 비공식 — 나중에 결정 추적 불가

### 구조

| 산출물 | 역할 | 위치 |
|--------|------|------|
| BACKLOG.md | 다음 작업 우선순위 단일 진실원 | `.claude/BACKLOG.md` |
| 계획 문서 | 작업별 산출물·접근법·결과 | `.claude/plans/YYYY-MM-DD-{slug}.md` |
| PROGRESS.md | 완료 이력 + 현재 git 상태 | `.claude/PROGRESS.md` |
| RETROSPECTIVE.md | 실패/사고 + 재발 방지 규칙 + **반영 위치** | `.claude/RETROSPECTIVE.md` |

### 의무 사항 (CLAUDE.md "개발 워크플로우"에 박힘)

- BACKLOG에 없는 작업은 먼저 BACKLOG 추가 후 진행
- 작업 종료 시 4단계(계획 결과 / BACKLOG 항목 제거 / PROGRESS 갱신) 누락 시 다음 세션 stale
- 회고에는 "재발 방지 규칙을 어디에 박았는지"(CLAUDE.md / 메모리 / hooks) 반드시 명시

### 트레이드오프

- 문서 5종 동시 관리 부담 ↑
- 그러나 다음 세션 진입 시 BACKLOG.md만 보면 무엇을 할지 즉시 명확 — 토큰·시간 절약

### 면접 답변

"1인 개발이지만 작업 진행을 즉흥으로 두면 다음 세션 시작 때마다 컨텍스트 복원에 시간을 씁니다. 백로그·계획·진행·회고를 분리해 단일 진실원을 만들고, AI 에이전트가 매 사이클 끝에 문서를 갱신하도록 의무화했습니다. 회고는 반드시 '재발 방지 규칙이 어디에 박혔는지'를 명시해서, 같은 실수가 반복되지 않도록 가드레일을 누적합니다."

## ADR-011: PR 생성 + 머지 풀 자동화 (SHA 검증 안전망) — v2 2026-06-13 갱신

### 결정 (v2 — 2026-06-13)

- PR 생성: Claude가 `gh pr create`로 자동 (사전 검증 6단계 체크리스트 통과 시)
- **PR 머지: Claude가 `gh pr merge --merge`로 자동 (SHA 검증 안전망 7단계 통과 시)**
- main 브랜치 보호 룰: PR 경로 강제, force-push/delete 금지 (approval 0)

### 결정 v1 (2026-06-10) — 번복됨

v1은 "PR 머지: 사용자가 GitHub 웹에서 직접"이었음. 시범 진행 직후 결정 번복.

### 번복 이유

v1 머지 자동화 선행 3조건(CI / 머신 리더블 메타 / 풀 사이클 멱등)이 안 갖춰졌으나, **시범에서 SHA 검증 안전망이 PR #19 패턴(PR 생성 후 추가 push 누적)을 실제로 잡음** → 사용자 최종 의도 재확인을 대체할 수 있음을 검증. 1인 환경에서 매번 GitHub 웹 클릭하는 비용 > 자동화 위험.

### 새 안전망: Commits SHA 자동 검증 (7단계)

```
gh pr view <num> --json commits --jq '.commits[].oid' | sort
↕ 비교
git log --format="%H" origin/main..origin/develop | sort
→ 일치: gh pr merge --merge
→ 불일치: 머지 중단 + 사용자 보고
```

이는 사용자가 GitHub 웹에서 매번 Commits 탭을 보던 절차를 코드로 강제. PR 생성 후 추가 push가 들어와 의도가 어긋난 경우 머지 직전에 잡힘. (실제로 PR #21 시범 중에 ADR/drift 정렬 커밋 2개가 의도 외로 누적된 것을 잡음 — `.claude/RETROSPECTIVE.md` 참조)

### 가드레일 4중 차단 (v2 갱신)

| 차단 위치 | 대상 |
|-----------|------|
| settings.local.json `deny` | `gh pr close`, force-push, `--no-verify` (단, `gh pr merge`는 v2부터 허용) |
| main 브랜치 보호 룰 | force-push, delete, 직접 push |
| 7단계 SHA 자동 검증 | 의도와 다른 변경 머지 차단 |
| RETROSPECTIVE.md | 자동 머지 확장 시 재검토 강제 |

### 머지 자동화 v3 확장 조건 (미래)

v2가 1인 환경에 충분하지만, 다음이 갖춰지면 더 안전한 v3로:
- CI 통과 필수 (현재 없음)
- PR description 머신 리더블 메타 강제
- 자동 머지 후 develop fast-forward 후처리

### 면접 답변

"PR 생성·머지를 둘 다 자동화했지만, 머지 직전에 Commits SHA 자동 검증을 박았습니다. PR 생성 시점의 의도 SHA와 머지 시점의 PR 실제 SHA를 비교해서 일치할 때만 머지. 실제로 시범 운영 중에 PR 생성 후 develop에 추가 push가 들어가 의도가 어긋난 케이스를 이 검증이 잡았습니다. 사용자가 매번 GitHub 웹에서 Commits 탭을 보던 절차를 코드로 옮긴 것입니다."

### 배경

이전 정책은 "gh CLI 사용 금지, PR 생성/머지 모두 사용자 직접". 결과:
- PR 생성이 매번 반복 작업
- **PR #19 사고**: push 누락된 채로 사용자가 PR 만들어 의도와 다른 변경분이 머지됨

### 분석

PR #19 사고의 본질은 "사용자 매번 검증 → 한 번 실수". 사용자가 매번 수동 검증하는 것보다 **자동화 안에 체크리스트를 박는 게 더 안전**:
1. `git fetch && git log origin/main..origin/develop` 자동 실행
2. 로컬 SHA = 원격 SHA 자동 검증 (push 누락 차단)
3. 머지 커밋 목록을 사용자에게 노출 + "진행?" 텍스트 확인 1회
4. PR 본문 두 섹션 자동 채움 (`## 변경 사항` / `## 상세`)
5. PR URL 반환 + 머지 전 Commits 탭 재확인 안내

### 머지 자동화는 왜 안 했는가

다음 3개 선행 조건이 갖춰지지 않음:
- CI 통과 필수 (현재 없음)
- PR description의 머신 리더블 메타 강제
- 자동 머지 후 PROGRESS 갱신·검증까지 풀 사이클 멱등

선행 조건 없이 머지 자동화하면 PR #19 같은 사고가 더 빠르게 재발. (자세한 검토: `.claude/RETROSPECTIVE.md` "PR 생성 자동화 도입" 회고)

### 가드레일 4중 차단

| 차단 위치 | 대상 |
|-----------|------|
| settings.local.json `deny` | `gh pr merge`, `gh pr close`, force-push, `--no-verify` |
| main 브랜치 보호 룰 | force-push, delete, 직접 push |
| Claude 자동 분류기 | deny 룰 자동 강제 |
| RETROSPECTIVE.md | 자동 머지 확장 시 재검토 강제 (선행 3조건 명시) |

### 면접 답변

"PR 생성은 자동화하되 머지는 사람이 직접 하도록 분리했습니다. 자동화의 가치는 '반복 작업 제거'와 '체크리스트 강제'에 있고, 머지의 가치는 '최종 의도 재확인'에 있습니다. 머지까지 자동화하려면 CI 통과 필수 등 선행 조건이 갖춰져야 하는데 그건 다음 단계입니다. 자동 분류기 deny + 브랜치 보호 룰 + 회고 문서 3중으로 자동 머지 확장 유혹을 차단했습니다."

## ADR-012: 위임 모드 — 사이클 간 자동 트리거

### 결정

사용자가 명시한 키워드로 위임 모드 진입 시, **한 응답 안에서 여러 8단계 사이클을 연속 처리**한다.

### 배경

2026-06-18 사용자 피드백: *"auto 모드로 워크플로우 돌리는 의미가 없는데? 작업을 효율적으로 돌리고 싶어"*

- 현재 구조: 매 사이클마다 사용자 트리거 필요 (반자동)
- 자율 모드(ADR-011 v2)는 사이클 안에서만 자율 — 사이클 간 트리거 비용이 자동화 의미를 무력화

### 분석

Claude Code는 본질적으로 턴제 구조. AI가 자율적으로 다음 턴 시작 불가. 단, **한 응답 안에서는 여러 사이클 진행 가능** — 8단계 후처리 완료 → 즉시 다음 사이클 1단계로 진입.

### 멈춤 조건 (가드레일)

- BACKLOG가 비거나 지정 범위(P0/P1 등) 처리 완료
- 큰 결정 필요 — Phase 분할, 외부 의존성 도입, 주요 설계 결정 (AI가 판단해서 멈춤)
- 빌드/lint/테스트 실패
- 자율 범위 밖 액션 (settings.local.json `deny`가 이미 차단)
- main 브랜치 보호 룰 (force-push/delete 차단)

### 위임 모드 vs 자율 모드 vs 기본 모드

| 모드 | 사이클 안 트리거 | 사이클 간 트리거 |
|------|------------------|------------------|
| 기본 | 매 단계 사용자 승인 | 사용자 명령 |
| 자율 (ADR-011 v2) | 자동 (deny 룰 차단) | 사용자 명령 |
| 위임 (ADR-012) | 자동 (자율 모드 포함) | 자동 (BACKLOG 따라) |

### 진입 키워드

룰화된 표현 (CLAUDE.md "위임 모드" 섹션):
- "BACKLOG P0 다 자동 진행"
- "BACKLOG가 빌 때까지"
- "다음 N개 사이클 자동"
- "오늘은 알아서 끝까지"

### 면접 답변

"AI 에이전트의 효율을 위해 두 단계 자동화를 분리했습니다. 자율 모드는 한 사이클 안에서 매 단계 사용자 승인을 제거하고, 위임 모드는 사이클 간 트리거까지 자동화합니다. 큰 결정은 멈춰서 합의받는 가드레일이 있어 의도와 다른 방향으로 폭주하지 않습니다. PR 자동 머지·main 보호 룰·deny 규칙 등 기존 안전망과 결합되어 1인 개발 환경에서 진정한 자동 워크플로우가 동작합니다."

## ADR-013: 자동 코드 리뷰를 8단계 사이클에 통합 (5.5단계)

### 결정

구현/커밋(3단계) 이후, PR 생성(6단계) 이전에 **`/code-review` 또는 그에 준하는 정적 점검**을 5.5단계로 의무화. lint/build만 통과하면 머지하던 관행 종료.

### 배경

2026-06-22 PR #22~#29 합산(8 PR, 52 파일, 2026 라인) 사후 `/code-review xhigh` 결과:
- CRITICAL 1건 (`@Async` tx race로 PENDING 영구 고착)
- HIGH 6건 (multipart YAML 위치, applyOcrResult 거짓 SUCCESS, Tesseract 동시성, Kafka fire-and-forget, timezone, ocrStatus 마이그레이션)
- 모두 빌드/lint는 통과 — 사람이 봐야 보이는 런타임/동시성/설정 버그

자동화는 빨라졌지만 **검증의 깊이가 lint 수준에 머무름**. 위임 모드까지 도입한 시점에 사후 발견은 핫픽스 사이클 비용을 부른다.

### 5.5단계 운영 방식

```
3. 구현 + 커밋
   ↓
5. 회고 (실패 있으면)
   ↓
5.5. 자동 코드 리뷰
     - 코드 변경 있는 사이클만 (docs-only PR은 skip)
     - /code-review high 이상 모드
     - 결과 분류:
       · CRITICAL → 동일 사이클 안에서 fix 후 5.5 재실행
       · HIGH    → 같은 PR에 포함 가능하면 즉시 fix, 아니면 별도 P0 핫픽스 PR
       · MEDIUM  → BACKLOG P1로 등록 + PR 본문에 명시
       · LOW     → BACKLOG P2 또는 무시 (회고 1줄)
   ↓
6. PR 생성
```

### 가드레일

- **CRITICAL이 fix 사이클에서 또 발견되면**: 자동 진행 중단, 사용자 합의 요청 (위임 모드 멈춤 조건)
- **위임 모드에서 HIGH 다수 발견 시**: 다음 사이클로 이월 금지 — 같은 응답 안에서 정리
- **docs-only/설정-only PR**은 5.5단계 skip (코드 동작 영향 없음)

### 트레이드오프

| 항목 | 비용 | 가치 |
|------|------|------|
| 사이클 당 ~5분 추가 (9 finder agent 병렬) | 토큰·시간 | CRITICAL 사후 발견 비용 >>> 사전 발견 비용 |
| 위임 모드 응답 길이 ↑ | 가독성 | 머지 후 핫픽스 PR 1건이 더 길어짐 |
| false positive 가능 | 검토 시간 | MEDIUM/LOW로 분류해서 무시/이월 가능 |

### 면접 답변

"AI 에이전트 자동화는 lint/build 통과를 검증으로 착각하기 쉽습니다. 빌드는 통과하는데 race condition / 스레드 비안전 / 설정 오류 / 마이그레이션 위험 같은 런타임 결함이 그대로 머지될 수 있어요. 이걸 막기 위해 8단계 사이클에 5.5단계로 자동 코드 리뷰를 박았습니다. 한 사이클 안에서 9개 finder agent가 병렬로 diff를 보고, CRITICAL 발견 시 같은 응답에서 fix 후 재검증합니다. 위임 모드의 멈춤 조건과 결합되어, 사후에 핫픽스를 만드는 비용보다 사전에 잡는 비용이 명백히 싸다는 게 검증됐습니다(2026-06-22 PR #30이 그 사례)."
