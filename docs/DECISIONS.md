# BuildFlow 기술 결정 기록 (ADR)

> Architecture Decision Records.
> 모든 기술 선택의 이유, 고려한 대안, 트레이드오프를 기록한다.
> Claude Code가 새 기술을 도입하거나 기존 결정과 충돌하는 선택을 할 때 참조한다.
> 면접에서 "왜 이 기술을 선택했나요?"에 바로 대답할 수 있도록 작성.

---

## ADR-001: MSA vs 모놀리식

### 결정
MSA 6개 비즈니스 서비스 + 3개 인프라 서비스 + 1개 챗봇 서비스

### 이유
- 포트폴리오 목적: Spring Cloud 생태계(Gateway, Eureka, Config, Kafka, Redis)를
  실무 수준으로 경험하고 증명해야 함
- 도메인 분리가 자연스러움: 견적/현장/매입/세금계산서는 각각 독립적인 비즈니스 맥락
- 학습 목적: 서비스 간 통신, 분산 트랜잭션, 이벤트 드리븐 패턴을 직접 겪어봐야 함

### 고려한 대안
- 모놀리식 → 빠르지만 포트폴리오 가치 낮음
- 모듈러 모놀리스 → 좋은 중간점이나 Spring Cloud 경험 불가
- 3~4개 서비스 → 현실적이지만 기술 경험 범위 좁음

### 트레이드오프
- 1인 개발에 MSA는 과도함. 개발 속도가 느려질 것
- 하지만 목적이 "학습 + 포트폴리오"이므로 의도적 선택
- 실사용에 문제가 되면 나중에 서비스를 
- 합칠 수 있음

## ADR-002: Kafka vs RabbitMQ vs Redis Pub/Sub

### 결정
Apache Kafka (KRaft mode)

### 이유
- 메시지 영속성: 디스크에 저장되어 소비자가 다운되어도 메시지 유실 없음
- 리플레이 가능: offset을 되돌려 과거 이벤트를 재처리할 수 있음
- 대용량 트래픽 포트폴리오: Kafka 경험이 백엔드 채용 시장에서 높은 가치
- KRaft mode: ZooKeeper 없이 운영 가능하여 로컬 환경 간소화

### 고려한 대안
- RabbitMQ: 가볍고 설정 쉬움. 하지만 메시지 리플레이 불가, 포트폴리오 가치 낮음
- Redis Pub/Sub: 가장 가볍지만 메시지 영속성 없음. 소비자 다운 시 유실

### 면접 답변
"RabbitMQ도 고려했지만, Kafka를 선택한 이유는 세 가지입니다.
첫째 메시지 영속성으로 유실 방지, 둘째 offset 기반 리플레이로 장애 복구,
셋째 Consumer Group으로 수평 확장이 가능하기 때문입니다."

## ADR-003: Redis 사용 범위

### 결정
캐시 + JWT 블랙리스트 + 분산락 (3가지 용도)

### 이유
- 캐시: 현장 목록/손익 조회가 빈번. DB 부하 줄이고 응답 속도 개선
- JWT 블랙리스트: Stateless JWT의 로그아웃 문제 해결
- 분산락: MSA 환경에서 동시 수정 방지 (Redisson)

### 패턴
- Cache Aside: 조회 시 Redis 확인 → 없으면 DB 조회 후 Redis 저장
- TTL 5분: 데이터 신선도와 캐시 효율의 균형점

### 면접 답변
"Redis를 세 가지 용도로 사용합니다.
Cache Aside 패턴으로 조회 성능 최적화, JWT 블랙리스트로 로그아웃 구현,
Redisson 분산락으로 동시 수정 방지입니다.
특히 분산락은 MSA에서 같은 견적서를 동시에 수정하는 것을 방지하기 위해 사용했습니다."

## ADR-004: Database per Service — 단일 MySQL 인스턴스

### 결정
MySQL 1개 인스턴스, 서비스별 스키마 분리

### 이유
- 로컬 개발 환경에서 MySQL 인스턴스 여러 개 띄우면 리소스 낭비
- 스키마 분리만으로도 논리적 격리 달성 가능
- 운영 환경에서 인스턴스 분리로 전환하려면 접속 정보만 바꾸면 됨

### 면접 답변
"로컬 환경 제약으로 MySQL 1개에 스키마를 분리했습니다.
각 서비스는 자기 스키마만 접근하고, 다른 서비스 데이터는 API로 조회합니다.
운영 환경에서 인스턴스를 분리하려면 Config Server의 접속 정보만 바꾸면 됩니다.
이게 Spring Cloud Config를 쓰는 이유이기도 합니다."

## ADR-005: Java 17 vs 21

### 결정
Java 17 (LTS)

### 이유
- Spring Boot 3.x의 최소 요구 버전
- 대부분의 기업 환경이 아직 17 기반
- Virtual Thread(21)는 이 프로젝트 규모에서 체감 어려움

### 트레이드오프
- 21의 Virtual Thread, Pattern Matching 등 최신 기능 못 씀
- 하지만 안정성과 호환성이 더 중요한 선택

## ADR-006: 챗봇 — RAG 방식 (벡터DB 없이)

### 결정
정형 데이터는 SQL 조회 → LLM 컨텍스트 주입. 벡터DB 미사용.

### 이유
- 데이터 대부분이 정형(MySQL): 현장명, 금액, 날짜, 상태
- 정형 데이터를 벡터로 변환하면 오히려 정확도 하락
- LLM function calling으로 의도 파악 → 적절한 API 호출 → 결과 주입이 더 정확
- 비정형 데이터(하자보증보험 PDF)가 많아지면 그때 벡터 검색 추가

### 면접 답변
"RAG라고 하면 보통 벡터DB를 떠올리지만, 이 프로젝트의 데이터는 대부분 정형 데이터입니다.
금액, 날짜, 현장명 같은 데이터를 벡터 임베딩하면 오히려 정확도가 떨어집니다.
LLM의 function calling으로 질문 의도를 파악하고, 적절한 SQL 쿼리 결과를
컨텍스트에 주입하는 방식이 이 도메인에서는 더 효과적입니다."

## ADR-007: 공내역서/견적서 — AI 자동 생성 안 함

### 결정
공내역서와 견적서는 각각 독립적으로 파일 업로드. AI가 하나를 보고 다른 걸 생성하지 않음.

### 이유
- 견적서의 단가는 현장 상황, 거래 관계, 시장 가격 등을 종합해서
  사람이 직접 판단해야 하는 영역
- 공내역서는 발주처가 보낸 원본 그대로 보관하는 문서
- 두 문서는 항목이 비슷할 수 있지만, 단가/금액은 완전히 다름
- 자동 생성하면 잘못된 견적이 나갈 위험

### 시스템에서의 역할
- 공내역서: 원본 파일 업로드 + 보관 + 뷰어
- 견적서: 파일 업로드 + 금액 데이터(total_amount) 저장 → 매출 계산 기준

## ADR-008: Gradle Groovy vs Kotlin DSL

### 결정
Gradle (Groovy)

### 이유
- 기존 경험이 Groovy 기반
- Spring Boot 공식 문서 예제가 Groovy 기준
- Kotlin DSL은 타입 안전성이 좋지만 학습 곡선 추가는 불필요

## ADR-009: 프론트엔드 상태 관리

### 결정
Zustand (클라이언트 상태) + TanStack Query (서버 상태)

### 이유
- Redux Toolkit은 이 규모에 과도한 보일러플레이트
- Zustand는 가볍고 직관적. 전역 상태(로그인 유저, 사이드바 토글 등)에 적합
- TanStack Query는 서버 데이터 캐싱, 자동 리페치, 로딩/에러 상태 관리가 내장
- 두 라이브러리의 역할이 겹치지 않아 조합이 깔끔
