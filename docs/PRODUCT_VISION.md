# BuildFlow 제품 비전

> 상태: 장기 방향성 기준 문서
>
> 갱신일: 2026-09-23
>
> 현재 구현 범위와 작업 우선순위는 `.claude/BACKLOG.md`를 우선한다.

## 1. 비전

BuildFlow는 건설·시공 업체의 현장 문서 관리에서 출발해, 사람과 조직마다 제각각인 파일·폴더·양식·업무 규칙을 원본 손상 없이 받아들이고 문서의 의미·관계·버전·근거를 정리해 주는 **유연한 정보관리 플랫폼**으로 발전한다.

플랫폼의 목적은 모든 사용자를 하나의 고정 양식에 억지로 맞추는 것이 아니다. 각 사용자가 이미 가진 정리 방식을 먼저 관찰하고, 공통 메타데이터와 사용자별 규칙을 분리해, 시간이 지날수록 더 잘 찾고 더 안전하게 보존하며 더 정확하게 판단할 수 있게 만드는 것이다.

### 한 줄 정의

> 흩어진 원본 정보를 안전하게 보존하고, 사람의 판단을 근거와 함께 축적해, AI가 정리를 돕되 최종 사실은 사람이 통제하는 정보관리 플랫폼.

## 2. 출발점과 확장 원칙

건설 도메인은 범용화를 위한 임시 예제가 아니라 첫 번째로 깊게 검증할 수직 도메인이다. 견적서·공내역서·세금계산서·보증보험과 같은 실제 자료에서 다음 문제를 해결하면서 범용 코어를 추출한다.

- 같은 이름의 파일이 수정본인지 별도 작업인지 알기 어렵다.
- 폴더, 날짜, 파일명, 문서 내부 표현이 사용자마다 다르다.
- 최신본만 남기면 판단 근거와 과거 이력이 사라지고, 전부 더하면 중복 집계가 생긴다.
- 문서 형식은 바뀌지만 현장·거래처·작업·버전과 같은 의미 관계는 계속 필요하다.

따라서 **건설 기능을 범용 기능으로 성급히 추상화하지 않는다.** 먼저 실제 자료로 반복 검증하고, 두 개 이상의 도메인에서 동일한 요구가 확인된 부분만 플랫폼 코어로 승격한다.

## 3. 제품 구조

### 3.1 범용 정보 코어 후보

Stage 0~2에서 실제 도메인 자료로 검증할 공통 기반 후보다. 건설과 두 번째 실제 도메인에서 같은 의미로 사용되고, 특정 도메인의 계산식에 의존하지 않으며, 기존 내보내기·복구 호환성을 유지하는 기능만 범용 코어로 승격한다.

| 영역 | 책임 |
|------|------|
| 원본 보존 | 원본 바이트, 원래 파일명·경로·수정 시각, MIME, 크기, 체크섬을 보존한다. |
| 출처·계보 | 누가·어디서·언제 가져왔고 어떤 추출기와 규칙을 거쳤는지 기록한다. |
| 버전·관계 | 수정본, 파생본, 첨부, 참조, 중복 후보 등 문서 간 관계를 논리적으로 연결한다. 관계 그래프는 개념 모델이며 그래프 DB 도입을 뜻하지 않는다. |
| 유연한 메타데이터 | 공통 필드는 고정하고 도메인별 필드는 버전이 있는 스키마로 확장한다. |
| 분류·검색 | 폴더뿐 아니라 유형, 태그, 대상 엔터티, 기간, 상태, 본문으로 찾는다. |
| 감사·정책 | 변경 이력, 사용자 확정, 보존 기간, 접근 정책, 내보내기 정책을 실행하고 감사한다. |
| AI 근거 | AI 제안, 신뢰도, 사용 근거, 모델·프롬프트 버전, 사용자 결정을 함께 기록한다. |

### 3.2 도메인 팩

업종이나 조직마다 달라지는 부분은 코어 후보에 하드코딩하지 않고 도메인 팩으로 둔다. 코어 후보가 정책 실행과 감사를 담당하고, 도메인 팩은 기본 규칙과 설정값을 제공한다.

- 문서 유형과 추출 필드
- 파일명·폴더명 해석 규칙
- 엔터티 유형과 관계 이름
- 검토·승인 흐름
- 계산식과 대시보드
- 보존·접근 정책
- AI 질문과 판단 기준

첫 번째 도메인 팩은 `건설 현장 관리`이며, 현장·거래처·견적·매입·세금계산서·보증보험·손익 규칙을 가진다. 핵심 사용자는 당분간 파일 기반 업무를 수행하는 소규모 조직의 실무 관리자다. 회계사무소·제조·연구자료·개인 기록 등은 확정 시장이 아니라 검증 후보이며, 수정본·관계 판단 문제가 반복되고 실제 데이터와 검토자를 확보할 수 있는 도메인을 다음 대상으로 선택한다.

### 3.3 Assistant

Assistant는 자동 정리기가 아니라 **근거를 제시하는 검토 보조자**다.

1. 규칙과 추출기로 확정 가능한 사실을 먼저 계산한다.
2. 과거에 사용자가 확정한 유사 사례를 검색한다.
3. `분류 후보·관계 후보·신뢰도·근거·추가 질문`을 구조화해 제시한다.
4. 사용자가 수정본·추가 작업·다른 대상·보류 등을 확정한다.
5. 확정 결과를 다음 판단에 재사용한다.

초기 학습은 모델 가중치 재학습보다 **확정 사례 검색과 규칙 보정**을 우선한다. 충분한 사례와 별도 검증셋이 쌓였을 때만 경량 분류기 또는 파인튜닝을 검토한다.

- 사례 검색과 학습의 기본 범위는 현재 워크스페이스 또는 테넌트 내부다.
- 고객 원본과 확정 사례는 명시적 동의 없이 공용 모델 학습이나 다른 조직의 판단에 사용하지 않는다.
- 공유 템플릿에는 원본, 거래처명, 금액 등 식별 가능한 사례를 포함하지 않는다.
- 보류·거절·취소·정정된 판단은 정답 사례에서 제외하고, 정정된 판단을 근거로 생성된 후속 제안은 다시 검토할 수 있게 연결한다.

## 4. 핵심 데이터 원칙

### 4.1 원본과 해석을 분리한다

- 관리 저장소의 원본 바이트는 보존 기간 동안 불변 객체로 취급한다.
- 파싱 결과, 태그, 관계, 정정 내용은 원본 위에 별도 계층으로 저장한다.
- 같은 바이트를 다시 가져오면 체크섬으로 식별하되 발견된 출처와 가져오기 관찰 기록은 모두 유지한다.
- 파서나 AI가 바뀌어도 원본에서 다시 처리할 수 있어야 한다.
- 승인된 삭제·법적 파기 시 원본을 제거할 수 있으며, 삭제 대상·승인·시각·체크섬을 포함한 파기 증적은 별도로 보존한다. 같은 원본 바이트를 여러 출처가 참조하면 모든 참조의 보존·삭제 조건을 확인한다.

### 4.2 원본 바이트·출처·관찰·추출을 분리한다

체크섬은 문서의 의미 ID가 아니라 바이트 객체 ID다. 동일 바이트가 여러 폴더·장치·시점에서 발견되는 경우 중복 저장을 피하면서도 각 출처를 잃지 않도록 다음 경계를 둔다.

```text
DocumentBlob: 불변 바이트, SHA-256, 크기, mediaType, 이동 가능한 storageKey
DocumentSource: 원본 이름, 장치 식별자, 상대 경로, 원본 수정 시각
ImportBatch/Observation: 어떤 스캔에서 언제 발견·복사·검증했는지
ExtractionRun: 파서·모델·프롬프트·결과 스키마 버전, 상태, 오류, 결과 해시
DocumentMetadata: 유형, 태그, 연결 엔터티, schemaKey, schemaVersion, 원시 추출 결과
```

원본 위치는 장치 식별자와 상대 경로로, 관리 저장소 위치는 불투명한 `storageKey`로 분리한다. 로컬 절대경로나 업무 엔터티 ID를 원본 객체의 식별자로 사용하지 않는다. 공통 필드까지 사용자마다 바꾸게 하면 검색·보존·감사가 깨지고, 모든 필드를 고정하면 다양한 양식을 수용할 수 없으므로 안정적인 공통 필드와 버전 관리되는 확장 필드를 함께 사용한다.

### 4.3 폴더가 아니라 관계를 중심으로 본다

폴더 구조는 중요한 출처 정보이지만 유일한 정답은 아니다. 하나의 문서는 현장, 거래처, 계약, 작업, 사람, 기간 등 여러 맥락에 동시에 연결될 수 있다. 원래 폴더 경로는 보존하면서 플랫폼에서는 컬렉션·태그·엔터티·관계로 여러 관점을 제공한다.

### 4.4 자동 판단과 업무 사실을 분리한다

- AI 제안은 확정 데이터와 별도 상태로 저장한다.
- 낮은 신뢰도나 충돌이 있는 항목은 검토함에 남긴다.
- 금액, 계약, 삭제, 보존 만료처럼 영향이 큰 작업은 명시적 확정 없이는 반영하지 않는다.
- 누가 어떤 근거로 무엇을 확정했는지 append-only 감사 기록을 남기고, 번복은 과거 기록을 덮어쓰지 않고 새 결정으로 연결한다.
- 현재 공유 관리자 단계에서는 `공유 관리자 계정 + 선택적 작업자 표시명/세션`을 기록하며, 작업자 구분이 없는 과거 기록을 특정 개인에게 억지로 귀속하지 않는다. 다중 사용자 단계부터 실제 사용자 ID와 역할 기반 감사로 전환한다.

### 4.5 문서 관계와 업무 반영을 분리한다

견적 영역은 다음 개념을 구분한다.

```text
EstimateWork: 하나의 공사 범위
EstimateRevision: 파일별 수정 이력
RelationProposal: 규칙·AI가 제안한 관계
ReviewDecision: 확정·거절·보류·번복 사건
AccountingEffectiveRevision: 손익에 반영되는 버전
```

- 한 `EstimateWork`의 손익 반영 버전은 사용자 확정 전 0개, 확정 후에도 최대 1개만 존재한다.
- 추가공사는 별도 `EstimateWork`로 만들고 각각 확정된 경우에만 반영한다.
- 다른 현장 분류는 문서 버전 관계가 아니라 대상 현장 연결 변경으로 처리한다.
- 확정된 수정 관계에는 순환이 없어야 한다.
- 파싱·AI 추출 금액은 후보 데이터이며 사용자가 확정한 회계 유효 견적 버전만 손익에 반영한다.

## 5. 보존 최적화 원칙

보존 최적화는 파일을 최대한 압축하는 것보다 **손실·중복·잠금 종속을 줄이고 복구 가능성을 증명하는 것**을 우선한다.

- 체크섬 기반 무결성 검사와 중복 탐지
- 원본과 미리보기·추출 텍스트·임베딩의 저장 계층 분리
- 자주 쓰는 자료와 장기 보존 자료의 hot/cold 계층화
- 데이터베이스와 파일 저장소의 함께 복구되는 백업
- 가져오기·관계 확정을 잠시 멈추거나 완료된 배치 checkpoint를 기준으로 DB와 파일 저장소의 일관된 시점 백업 생성
- DB가 참조하는 불변 Blob을 모두 복사한 뒤 내부 백업 manifest에 객체 ID, 체크섬, 크기, 저장소 키, 스키마 버전을 기록
- 휴대용 내보내기는 내부 `storageKey` 대신 묶음 내부 `packageRelativePath`를 사용하고, 운영 저장소와 다른 물리 대상에 백업
- 정기적으로 빈 환경 복원 후 모든 체크섬·참조 ID·회계 유효 버전과 손상 여부를 검증
- 원본 + 출처 + 추출 이력 + 메타데이터 + 관계 후보 + 확정·번복 결정 + 감사 이력 + 체크섬 manifest를 개방형 묶음으로 내보내기
- 사용자 또는 조직이 다른 시스템으로 이동할 수 있는 데이터 이동성 보장
- 보존 기간 만료, 법적 보존, 삭제 요청과 백업본의 삭제 반영 시점을 구분하는 정책 엔진

Stage 1에서는 외부 원본을 읽기 전용으로 다루고 검증된 관리 저장소 사본을 관리 기준본으로 삼도록 구현한다. 이후 실제 규모와 운영 요구에 따라 객체 저장소, 저장 암호화, 다중 복제, 테넌트별 보존 정책으로 확장한다.

## 6. 단계별 로드맵

### Stage 0 — 건설 실사용 완성

- 손익 집계와 수정·삭제 정책의 신뢰성 확보
- 현장 한 건의 전체 업무 흐름 검증
- 실제 USB 자료를 이용한 문제 목록 수집

### Stage 1 — 문서 기반과 사례 기억

- DB 마이그레이션·백업/복구 체계를 선행조건으로 확인
- 읽기 전용 가져오기 배치와 원본 문서 저장소
- 원본 메타데이터 기록 → 임시 복사 → 원본/사본 SHA-256 대조 → 원자적 승격 → 추출 → 검토 대기 흐름
- `DocumentBlob`·`DocumentSource`·`ImportBatch/Observation`·`ExtractionRun` 분리
- 문서 버전·관계 후보 및 사용자 검토함
- 확정 사례 기반 Assistant
- 원본·출처·추출·관계·결정·감사 통합 내보내기와 빈 환경 복구 검증
- 형식·크기 제한, path traversal·symlink 차단, 매크로/실행 파일 비실행, 민감정보 로그 금지, 로컬 ACL과 백업 보호를 포함한 가져오기 위협 모델

### Stage 2 — 구성 가능한 워크스페이스

- 문서 유형·필드·관계·분류 규칙을 템플릿으로 정의
- 사용자별 파일명·폴더 해석 규칙
- 검토 흐름과 보존 정책 구성
- 건설 이외의 두 번째 실제 도메인으로 코어 경계 검증

### Stage 3 — 플랫폼 운영

- 조직·테넌트 격리, 역할 기반 권한, 암호화 키 분리
- API·웹훅·파일 동기화 커넥터
- 대용량 비동기 처리, 저장 계층화, 감사·관측성
- 도메인 팩과 커넥터의 배포·버전 호환 체계

### Stage 4 — 정보 운영 생태계

- 사용자가 자신의 데이터 규칙을 공유하거나 판매할 수 있는 템플릿 생태계
- 조직별 지식 Assistant와 자동화 워크플로우
- 플랫폼에 종속되지 않는 표준 내보내기·이관 도구

## 7. 일상 사용 흐름

```text
수집 → 가져오기 검증 → 검토함 → 관계 확정
     → 현장·업무 연결 → 검색·질문 → 내보내기·복구
```

- **수집**: 기존 폴더를 바꾸지 않고 자료를 선택한다.
- **가져오기 검증**: 원본이 변경되지 않았고 관리 사본이 완전한지 확인한다.
- **검토함**: AI 후보와 실제 차이를 나란히 보고 애매한 항목만 판단한다.
- **관계 확정**: 수정본·추가 작업·다른 대상을 명시적으로 구분한다.
- **업무 연결**: 확정된 자료만 현장과 손익 등 업무 사실에 반영한다.
- **검색·질문**: 위치를 기억하지 않고 출처와 근거까지 함께 찾는다.
- **내보내기·복구**: 플랫폼 밖에서도 원본과 맥락을 잃지 않고 복원한다.

## 8. 성공 기준

### 현재 도메인

- 필요한 문서를 위치를 기억하지 않고 찾을 수 있다.
- 수정본과 추가 작업을 구분하고 중복 손익 반영을 막는다.
- 원본과 판단 근거를 언제든 확인하고 되돌릴 수 있다.
- USB 장애나 시스템 재설치 후에도 복구 절차가 검증되어 있다.

### 범용 플랫폼

- 새 조직의 기존 폴더를 강제 개편하지 않고 가져올 수 있다.
- 코드 변경 없이 새 문서 유형과 필드를 정의할 수 있다.
- AI가 낸 결과와 사람이 확정한 사실을 명확히 구분한다.
- 사용자가 모든 원본과 구조화 데이터를 완전하게 내보낼 수 있다.
- 두 번째 도메인에서도 공통 코어를 수정하지 않거나 최소 변경으로 적용할 수 있다.

### Stage 1 종료 기준

- 가져오기가 외부 원본에 수행한 쓰기·이름 변경·삭제 0건
- 복사 전후 크기·수정 시각 또는 해시가 달라진 원본의 성공 처리 0건; 감지 시 보류 후 안전하게 재실행
- 관리 저장소 원본의 SHA-256 재검증 성공률 100%
- 동일 바이트 재가져오기 시 Blob 중복 없이 출처·관찰 이력 보존
- 복사 중 원본 변경·중단 시 성공 처리되지 않고 안전하게 재실행 가능
- 수정본 3개를 묶어도 한 작업의 손익 반영 버전은 정확히 1개
- 추가공사는 별도 작업으로 분리되어 각각 확정된 경우에만 반영
- AI 제안 거절·사용자 결정 번복이 다음 정답 사례에서 제외됨
- 빈 환경에 내보내기 묶음을 복원한 뒤 모든 체크섬과 출처·관계·결정 건수 및 참조 무결성 일치
- 실제 현장 하나의 가져오기부터 검색·손익 반영까지 완료하고 문서 탐색·분류 시간을 파일럿 전후로 측정

## 9. 하지 않을 것

- 범용성을 이유로 현재 건설 실사용 완성을 미루지 않는다.
- 모든 문서를 하나의 고정 분류 체계에 강제로 맞추지 않는다.
- 원본을 AI 결과로 덮어쓰거나 이름을 임의 변경하지 않는다.
- 충분한 확정 사례와 평가 없이 AI가 자동으로 금액·관계·삭제를 확정하지 않는다.
- 사용자가 데이터를 꺼낼 수 없는 폐쇄형 저장 구조를 만들지 않는다.
- 실제 부하와 팀 규모의 필요가 생기기 전에 서비스를 무조건 추가하지 않는다.
