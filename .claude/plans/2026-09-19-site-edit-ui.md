## 목표

현장 상세에서 현장명·거래처·주소·공사 기간·메모를 수정하고, 오류 시 입력을 보존한다. 상태 변경은 기존 별도 동선을 유지한다.

## 배경 / 동기

백엔드 PUT와 프론트 mutation은 있지만 화면에 수정 진입점이 없어 입력 오류를 실사용자가 보정할 수 없다.

## 접근법

1. `SiteUpdateRequest`의 PUT 전체 교체 의미를 타입과 폼에 반영한다. 거래처 제거와 선택 필드 비우기가 서버에서 null로 처리되는지 계약을 확인한다.
2. 현장 상세에 수정 버튼과 사전 채움 모달을 추가한다. 저장 중 중복 요청·닫기를 막고, 성공 시 site 쿼리 무효화로 헤더를 갱신한다.
3. MSW PUT가 거래처 객체 해석·전체 필드 교체·404 계약을 맞추도록 고치고, UI/API 계약 테스트를 추가한다.
4. 프론트 테스트·lint·build와 독립 코드 리뷰를 거쳐 PR 절차를 수행한다. 실사용 현장 데이터는 테스트 목적으로 변경하지 않는다.

## 리스크 / 모르는 것

- PUT는 부분 수정이 아니다. 선택 필드를 비운 경우 값 제거가 의도되므로 전체 폼 값을 보내야 한다.
- 실서비스 PUT 스모크는 사용자 현장 자료를 변경할 수 있어 수행하지 않는다.

## 테스트 / 검증

기존 값 사전 채움, 거래처 제거와 기간 비우기, 유효성 검사, 중복 제출 차단, 실패 후 재시도, MSW PUT→GET 결과를 검증한다.

## 결과 (작업 후 기록)

현장 상세에 수정 버튼과 사전 채움 모달을 추가하고 백엔드 전체 교체 PUT에 맞춘 `SiteUpdateRequest`를 보낸다. 거래처·날짜·주소·메모를 비우면 명시적 null로 전송한다. 저장 중 중복 요청과 닫기를 방지하고, 실패 시 입력을 유지한다. MSW도 PUT의 거래처 해석·null/404 계약과 GET 반영을 맞췄다. 프론트 42개 테스트, lint, build가 통과했고 독립 리뷰에서 HIGH/P1 이상 결함이 없었다. 프론트 컨테이너 재빌드 후 HTTP 200, 미인증 현장 API 401을 확인했다. 실제 현장 PUT은 데이터 변경 위험 때문에 수행하지 않았다. PR 병합 결과는 후처리에서 기록한다.
