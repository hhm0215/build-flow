# 세금계산서 입금 확인 실서버 계약 수정

- **시작일**: 2026-09-20
- **BACKLOG 항목**: P0 실사용 UI 라이프사이클 연결 — 오류 처리
- **예상 규모**: S
- **상태**: DONE

## 목표
기존 매출 세금계산서 ‘입금 확인’ 버튼이 실서버의 필수 JSON 본문 계약을 만족하도록 고치고, 실패 시 화면에 오류를 보여 재시도할 수 있게 한다.

## 배경 / 동기
프론트 `PATCH /api/v1/taxes/{id}/confirm-payment`는 본문 없이 호출하지만 백엔드는 `@RequestBody PaymentConfirmRequest`를 필수로 받는다. MSW가 요청 본문을 검증하지 않아 개발 화면에서 문제를 숨긴다.

## 접근법
- 프론트 mutation이 `paymentDate` JSON 본문을 보내 백엔드 계약을 만족한다. 확인 모달의 날짜 기본값은 브라우저의 오늘이며 실제 입금일을 바꿀 수 있다. 기존 서버 API 서명은 변경하지 않는다.
- 확인 모달에서 대상·금액을 명시하고, 중복 제출·진행 중 닫기를 막는다. 오류 응답을 표시하고 재시도를 허용한다.
- 서버는 읽을 수 없는 JSON 요청을 400으로 분류하고, MSW PATCH가 본문 존재·미확정 상태·404/409를 실제 계약에 맞춰 검증한다. 기존 UI의 SALES 전용 노출은 목록 테스트로 고정한다.
- 프론트 UI/API/MSW 테스트와 실서비스의 비영속 404 스모크(가능한 경우)를 수행한다.

## 리스크 / 모르는 것
- 실제 입금확인은 영속 DB와 Kafka 이벤트를 변경하므로 스모크에서 테스트 인보이스를 만들지 않는다. 없는 ID에 유효한 날짜 본문을 보내 요청 본문 파싱 경계만 확인한다.
- 백엔드는 PURCHASE 확인도 허용하지만 UI는 기존처럼 SALES만 노출한다. 확정 후 수정·삭제 정책은 별도 사용자 결정 전까지 건드리지 않는다.
- Kafka 알림 중복·실패는 P0 신뢰성 작업에 남는다.

## 테스트 / 검증
- API 요청 body `paymentDate`와 MSW body 검증/404/409.
- 모달 취소·성공·실패 후 재시도·중복 제출.
- 프론트 lint/test/build, 전체 Gradle test, 필요 시 Docker tax-service 비영속 404 스모크.

## 결과 (작업 후 기록)
프론트는 입금일 JSON 본문을 전송하고, 모달에서 입금일 선택·중복 제출 방지·오류 표시와 재시도를 제공한다. MSW는 빈/잘못된 본문·존재하지 않는 ID·중복 확인을 실제 API에 맞춰 처리한다. 백엔드는 읽을 수 없는 JSON을 400으로 반환한다.

프론트 lint·Vitest 72개·build 및 전체 Gradle test 통과. 정적 코드 리뷰에서 요청 DTO, 오류 분류, UI 상태 전환, 캐시 무효화 범위를 점검했고 차단 수준 지적은 없다. 독립 리뷰의 1차 검토도 HIGH/CRITICAL 지적이 없었으나 최종 재검토는 도구 사용 한도로 완료되지 않았다. Docker 엔진 연결이 중단되어 tax-service 재기동/실서버 404 스모크는 보류했으며 단위 테스트 결과를 실서버 검증으로 간주하지 않는다.
