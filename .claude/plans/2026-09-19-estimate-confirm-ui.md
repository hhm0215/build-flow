- **BACKLOG 항목**: P0 — 실사용 UI 라이프사이클 연결
- **예상 규모**: S (L 작업의 두 번째 수직 슬라이스)
- **상태**: DONE (UI 계약·단위 테스트 완료, 실서비스 이벤트 검증은 Kafka P0 이후)

## 목표

작성 중인 견적서를 목록에서 확인 후 확정할 수 있게 한다. 확정 성공 시 상태를 갱신하고, 실패 시 이유를 표시하며 다시 시도할 수 있어야 한다.

## 배경 / 동기

백엔드와 프론트 API 훅에는 견적 확정 계약이 있지만 화면에서 호출하지 않는다. 따라서 UI만으로는 확정 이벤트와 손익 집계 흐름을 시작할 수 없다.

## 접근법

1. 견적 목록의 DRAFT 행에만 확정 버튼을 제공한다.
2. 확정 전 되돌릴 수 없는 상태 전환임을 명시하는 확인 모달을 둔다. 처리 중 중복 요청과 닫기를 막는다.
3. 기존 `useConfirmEstimate` mutation을 사용한다. 성공 시 쿼리 무효화로 상태가 갱신되며, 실패 시 서버 오류를 모달에 표시한다.
4. UI 회귀 테스트와 프론트 lint/test/build를 실행한다.

## 리스크 / 모르는 것

- 실제 확정 API는 Kafka `estimate.parsed`를 발행한다. 현재 소비자 멱등성·재시도 등 P0 신뢰성 작업이 남아 있으므로 실데이터로 확정하지 않는다. 이 슬라이스는 화면 계약과 모킹된 동작까지만 확인한다.
- 견적 수정·삭제 및 초안 제외 기준은 같은 P0 백로그의 후속 작업으로 남는다.

## 테스트 / 검증

- 단위 UI 테스트: 초안에서만 확정 가능, 취소 시 요청 없음, 성공 시 닫힘, 서버 실패 시 오류 유지 및 재시도.
- `bun run lint`, `bun run test`, `bun run build`, `git diff --check`.

## 결과 (작업 후 기록)

견적 목록에서 DRAFT 행에만 확정 버튼을 추가하고 확인 모달에서 기존 확정 API mutation을 호출한다. 중복 요청·진행 중 닫기를 막고, 서버 실패 시 오류를 표시하며 재시도할 수 있다. 현장 허브 및 상세의 프론트 손익 합계는 확정된 견적만 포함한다. 프론트 lint, Vitest 27개, 프로덕션 빌드가 통과했다. 프론트 컨테이너를 재빌드·재기동하고 HTTP 200을 확인했다. 빌드의 기존 대형 번들 경고는 P2에 남는다. 백엔드 Kafka 소비 신뢰성 P0가 남아 있어 실제 견적 확정·손익 반영 스모크는 수행하지 않았다.
