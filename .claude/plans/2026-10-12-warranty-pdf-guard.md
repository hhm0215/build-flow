# 보증보험 PDF 업로드·OCR 입력 안전성

- **시작일**: 2026-10-12
- **BACKLOG 항목**: 공개 파일럿 CRUD 실동선 검증·결함 수리
- **예상 규모**: M
- **상태**: 구현·PR 병합·공개 테스트 파일럿 배포 완료, 실제 합성 PDF/OCR 검증 대기

## 목표
공개 파일럿의 PDF 업로드에서 형식·크기·페이지/렌더링 자원 한도를 서버가 검사하고, 거부된 파일은 보관하거나 OCR 작업으로 넘기지 않는다. 파일 경로·OCR 원문/보험사·예외 상세가 로그에 남지 않게 한다.

## 배경 / 동기
현재 브라우저의 `.pdf`·20MB 안내와 multipart 한도는 있지만 서비스는 입력을 검증하지 않고 원본 확장자로 저장한다. 비동기 OCR은 페이지 수·렌더링 크기 제한 없이 처리하고 경로·보험사·예외 상세를 로그에 남긴다. 실제 PDF/OCR 성공은 여전히 미검증이다.

## 접근법
업로드 입력의 서버측 바이트·형식·페이지 상한을 적용하고 저장 파일명을 UUID 기반 `.pdf`로 고정한다. PDFBox OCR 전에 페이지/렌더링 상한을 검사한다. 과도한 입력의 저장·DB PENDING 생성·OCR 호출을 방지하고, 테스트에는 합성 PDF만 사용한다. 이미 존재하는 보증정보와 USB/VPS 데이터는 수정하지 않는다.

## 리스크 / 모르는 것
PDFBox 파서는 악성 파일을 읽는 단계도 비용이 든다. 한도는 완전한 샌드박스가 아니므로 공개 파일럿에서만 테스트하고 실제 업무 파일 허용/실데이터 승격은 보류한다. 삭제/보관, 임의 `siteId`, DB+파일 복구 게이트는 별도 작업이다.

## 테스트 / 검증
빈 파일·PDF가 아닌 바이트·거짓 파일명·한도 초과·페이지 초과가 DB 저장/OCR 전에 거부되고 파일이 남지 않는지 확인한다. 정상 합성 PDF는 PENDING 생성과 OCR 호출까지 테스트한다. 비동기 OCR은 페이지·픽셀 상한을 검사한다.

## 로컬 결과
`notification-service:test`, 프론트 lint·133개 테스트·build PASS. 20 MiB, PDF 구조/암호화, 10페이지, 300 DPI 렌더 1,200만 픽셀/변 5,000픽셀, 텍스트 20만 자 상한. 원본 확장자를 저장 이름/응답에 사용하지 않는다. `createFromOcr`의 클래스 read-only 트랜잭션 상속을 해제하고, OCR 결과는 별도의 짧은 잠금 트랜잭션에서 `PENDING`일 때만 반영한다. 합성 JPA 테스트에서 enqueue 전 DB 조회와 삭제 후 콜백 비재생성을 확인했다. 30분 초과 `PENDING`은 정기적으로 `FAILED`로 전환해 재시작 유실 상태를 해소한다.

## 잔여 게이트
PDFBox 파서 내부 CPU/압축 해제, Tesseract native 작업의 hard timeout·프로세스 격리는 미구현이다. 공개 파일럿 실제 합성 PDF/OCR 성공·장애 복구, DB+업로드 동시 외부 백업/격리 복원 전에는 실데이터 승격 금지. PR #94와 후속 문서 PR #95의 병합 main CI 6개가 각각 통과했고, 2026-10-13 테스트 VPS에 notification-service만 반영해 이미지·볼륨·health·HTTPS·401을 검증했다. 이는 실제 OCR 성공 증거가 아니다.
