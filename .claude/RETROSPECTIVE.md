## 2026-06-10 — PR 생성 자동화 도입 (사고 아닌 의사결정 회고)

**무엇이 일어났는지**:
- 첫 시범 사이클 완주 직후, 사용자가 "PR 머지도 자동화 가능한가?" 질문

- main 브랜치 보호 룰 신설 (PR 경로 강제 + force/delete 금지, approval 0)

**왜 자동화했는가**:
- PR 생성 자체는 반복 작업이라 자동화 가치 큼
- PR #19 사고의 본질은 "push 누락 + Commits 탭 미확인"인데, 이걸 **자동화 안에 체크리스트로 박는 게 사용자가 매번 수동으로 검증하는 것보다 안전**

**어떤 위험을 어떻게 막았는가**:
- 위험: Claude가 실수로 머지 → `gh pr merge` deny 룰 + main 보호 룰 이중 차단
- 위험: 의도 안 한 커밋이 PR에 포함 → 워크플로우 6단계의 `git fetch` + push 누락 검증 체크리스트 의무화
- 위험: 자동화 범위가 시간이 지나며 슬금슬금 머지까지 확장 → 이 회고 자체가 미래의 본인에게 "왜 머지 자동화는 하지 않았는지" 근거 제공

**향후 경계**:
- 자동 머지로 확장하려는 유혹이 생기면 이 회고 + PR #19 사고를 다시 읽을 것
- 자동 머지를 도입한다면 최소 다음 3개가 선행되어야 함:
  - CI 통과 필수 (현재 없음)
  - PR description에 "어떤 BACKLOG 항목인지" 머신 리더블 메타 강제
  - 자동 머지 후 PROGRESS.md 갱신·검증까지 풀 사이클이 멱등하게 동작

**반영 위치**:
- `.claude/settings.local.json` — gh PR 생성/조회 allow, 머지/클로즈/force-push deny
- `CLAUDE.md` "## Git" — PR 생성 가능·머지 금지로 갱신
- `CLAUDE.md` "## 개발 워크플로우" — 6단계 PR 생성 + push 누락 검증 체크리스트 추가
- GitHub main 브랜치 보호 룰 (force/delete 금지 + PR 필수, approval 0)

## 2026-06-13 — 활성 PR 동안 develop 추가 push로 PR에 의도 외 커밋 누적

**무엇이 일어났는지**:
- 2026-06-10 PR #21 생성 직후, 같은 자율 모드 흐름에서 ADR-010/011 정식화(`a5b1a3a`) + drift 정렬(`33c532f`) 2 커밋을 develop에 추가 push
- PR은 head=develop을 추적하므로 추가 커밋이 PR #21에 자동 흡수
- 의도(`c0f66d7`까지 4 커밋)와 PR 실제 내용(6 커밋)이 어긋남
- 2026-06-13 머지 자동화 시범 직전 SHA 검증 안전망이 불일치를 잡음

**원인**:
- PR 생성 시점에 "후속 정리도 곧 이어질 수 있다"는 인지가 없었음
- 활성 PR이 있는 동안 develop에 push해도 PR과의 동기화를 생각 안 함
- PR #19 사고("push 누락")의 거울상 — "push 누락" 대신 "추가 push 누적"

**재발 방지 규칙**:
- 활성 PR이 있는 동안 develop에 추가 push 시 다음 중 하나:
  - PR 본문을 즉시 갱신해서 추가 변경 명시 (`gh pr edit --body`)
  - 또는 추가 push 미루기 (PR 머지 후 진행)
- 머지 직전 SHA 검증(7단계)으로 최종 안전망 — 자동 차단

**반영 위치**:
- `CLAUDE.md` "개발 워크플로우" 7단계 — SHA 검증 + 불일치 시 머지 중단 명시
- `CLAUDE.md` IMPORTANT 룰 — "활성 PR 있는 동안 develop 추가 push 시 본문 갱신 + 재검증"
- `docs/DECISIONS.md` ADR-011 v2 — 안전망의 가치 증명 케이스로 인용

## 2026-06-13 — ADR-011 결정 번복 (PR 머지 자동화로 확장)

**무엇이 일어났는지**:
- 2026-06-10 ADR-011 v1: "PR 머지는 사용자가 GitHub 웹에서 직접" 결정
- 2026-06-13 사용자가 "가드레일 규칙 무너뜨리고 자동화 워크플로우로 가려고 한건데" 표명
- 시범 1회 진행 → SHA 검증 안전망이 실제 위험을 잡는 것 확인 → ADR-011 v2로 결정 번복

**번복의 합리성**:
- v1 머지 자동화 선행 3조건(CI / 머신 리더블 메타 / 풀 사이클 멱등) 중 1·3은 안 갖춰짐
- 그러나 1인 환경에서 매번 GitHub 웹 클릭하는 비용이 자동화 위험보다 큼
- SHA 검증 안전망이 v1의 "사용자 최종 의도 재확인"을 대체 가능 — 시범에서 검증됨

**규칙 관리의 교훈**:
- ADR 번복 자체는 정상. 단, 번복 전 ADR이 "왜 그렇게 결정했는가"의 근거를 명확히 남겨둔 게 도움됨
- 번복 시 v1을 지우지 않고 "v1 — 번복됨" 표기 + 번복 이유 + 새 안전망을 같은 ADR에 v2로 추가
- 회고에 의사결정 변경을 따로 기록해서, 미래의 v3 확장 유혹 시 이 패턴을 다시 참조

**반영 위치**:
- `docs/DECISIONS.md` ADR-011 v2 — v1 본문 유지하면서 v2로 확장
- `CLAUDE.md` "Git" + "개발 워크플로우" — 머지 자동화 + 7단계 SHA 검증 + 8단계 후처리
- 이 회고 자체 — "ADR 번복 규칙" 사례

## 2026-07-15 — 같은 포트의 이중 리스너(네이티브 vs 도커 Ollama)가 만든 침묵의 404

**무엇이 일어났는지**:
- chat Phase 2 런타임 검증에서 `/api/chat` 404 — 하지만 `curl localhost:11434`은 정상 응답(qwen2.5:7b 존재)
- 원인: 11434에 **리스너가 둘** — 도커 Ollama(IPv6, qwen2.5:7b)와 7/7 사용자가 설치한 호스트 네이티브 Ollama(IPv4 127.0.0.1, qwen3:8b만 보유). curl은 IPv6로, Java WebClient는 IPv4로 붙어 **같은 주소가 프로세스마다 다른 서버**에 연결됨. 네이티브에 qwen2.5:7b가 없어 404
- Phase 1 검증(7/4)은 네이티브 Ollama 설치 전이라 통과 — 환경 드리프트가 잠복 버그를 만든 또 하나의 사례

**원인**:
- "포트가 응답한다 = 내가 의도한 서버다"라는 가정. 듀얼스택(IPv4/IPv6)에서는 성립하지 않음
- 진단 도구(curl)와 애플리케이션(Java)의 주소 해석 순서가 달라 **재현 실험 자체가 거짓 음성**을 냄

**재발 방지 규칙**:
- 포트 충돌/오동작 의심 시 `lsof -i :PORT -sTCP:LISTEN`으로 **리스너 목록부터** 확인 (IPv4/IPv6 구분 포함)
- 원인 판정은 클라이언트 재현이 아니라 **서버 쪽 액세스 로그**(도착 여부)로 — 이번엔 docker Ollama GIN 로그에 요청이 아예 없다는 사실이 결정적이었음
- 로컬 검증 시 `OLLAMA_URL=http://[::1]:11434`로 도커 지정 (또는 네이티브 Ollama 중지)

**반영 위치**:
- `.claude/plans/2026-07-04-chat-service.md` "검증 중 발견한 환경 함정" — 런북에 이중 리스너·nginx 포트 점유·DB_PASSWORD·config-server 우회 4건 기록
- PROGRESS "다음 세션 진입점" 로컬 실행 노하우 갱신
- 이 회고 — 포트 진단 절차(리스너 확인 → 서버 로그 확인) 명문화
